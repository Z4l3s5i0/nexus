# Modular experiment suite

`experiments/run.sh` is the primary entry point for the five experiment modules. It prompts for a selection, runs the shared setup once, then dispatches modules sequentially in the order entered. Select `6` (or `all`) for the full suite in standard order: runtime, empty-block, startup, compliance, and size comparison. The full-suite selection uses the matrix described below; experiments continue after an individual run fails. Select `8` (or enter `test`) for one quick pass through the variants, or select `7` to enter evaluation mode and choose which saved experiment results to reevaluate without rerunning workloads or setup.

```bash
bash experiments/run.sh
```

Enter a comma-separated selection such as `3,1,5` to run startup, runtime, then size comparison. For reevaluation, enter `7` and then select `1–5`, a comma-separated list, or `6` for all module types. Evaluation validates each saved run's completion status and required artifact schemas before regenerating its report; failed, interrupted, or incomplete results are reported as errors while other selected runs are still checked. The saved samples and measurements are reused, and no clients, workloads, Hive suites, or source measurements are rerun. `bash experiments/run.sh --help` displays the menu. `experiments/setup.sh` can also be run directly; without the runner’s selection it prepares dependencies for all five modules.

The `test` preset runs each test variant once with short settings: all five runtime workloads on one node per client, all 20 empty-block client/workload combinations with one transaction sample, all five startup configurations once, both default Hive clients once (600-second per-client timeout), and one size comparison. It is intended to finish in under an hour when the required tools, client artifacts, and Docker images are already available; first-time dependency installation and image/build preparation can take longer. The preset still uses real clients, workloads, setup, and result recording, and does not replace the full benchmark suite.

The default full runtime matrix automatically resets generated network data before each task and removes it during teardown, so stale artifacts do not block later runs; an already-running shared network is still never reset. For other runtime, empty-block, and startup runs, pass `--reset-network` to allow clearing pre-existing generated network data. Startup clears stopped shared-network data before its isolated client runs; it refuses to remove data while that network is running. For empty-block, the flag also skips the separate reset-consent prompt. It can be combined with `--detach`.

The runner defaults to `--verbosity info`, which shows experiment progress on the console and writes setup and module details to their respective log files. Use `--verbosity debug` to stream all output to the console as well as recording it in those files; either form `--verbosity debug` or `--verbosity=debug` is accepted.

Each experiment run writes result artifacts to `experiment-results/<module>/<run-id>/`. The runner exports a common base `EXPERIMENT_RUN_ID` and output root to all selected modules; runtime and empty-block derive distinct run IDs for each matrix task. Generated result directories are ignored by Git; source scripts under `experiments/` are tracked.

Every invocation of `experiments/run.sh` also creates `experiment-results/logs/<session-id>/`. `overview.csv` records the status and failure reason for shared setup and every experiment task; tasks not reached because setup failed are marked skipped. `runner.log` records the menu, selected modules, configuration messages, and dispatch progress. A run invocation records shared setup output and its exit status in the single `setup.log`; each selected experiment has its own subfolder and `run-<run-id>.log`, so one module's output cannot be mistaken for another's. Evaluation-only runs write each report invocation to that experiment's `evaluation-<number>.log` and do not create a setup log. In info mode, detailed command output is captured in these files instead of the console; in debug mode, standard output and errors are streamed to the console while being captured. Command arguments are intentionally omitted from log headers to avoid recording secrets such as the empty-block private key. Detailed client, workload, Hive, and collector logs remain in their experiment result folders.

## Plot saved experiment results

Generate client-comparison charts from saved reports without rerunning workloads:

```bash
python3 experiments/plot_results.py --results-dir exp/experiment-results
```

The script writes module-specific SVG charts, `index.html`, and the aggregated `plot_data.csv` under `<results-dir>/plots/`. It supports runtime, empty-block, startup, compliance, and size results; pass `--module runtime` (repeatable) to limit which modules are plotted, or `--output-dir` to choose another destination. If `--results-dir` is omitted, `EXPERIMENTS_OUTPUT_ROOT` is used when set, otherwise the script checks `experiment-results/` and then `exp/experiment-results/`.

Empty-block latency plots show response versus transaction target on a log-scaled x-axis and mark an exploratory knee candidate only when there are enough target levels; this geometric marker is not a capacity guarantee. Exact-match and completed-burst rates use client-by-target heatmaps. A separate completed-burst heatmap labels the mean number of blocks spanned per target; green is best at one block, and red marks five or more blocks (the color scale caps at five). Partial/incomplete bursts are excluded from this spread metric, while the completion-rate heatmap shows them separately. Runtime throughput uses a line plot over cluster size, while commit ratio and container CPU/memory use heatmaps. Runtime charts group standalone client runs with the same workload profile and node count for direct client comparisons; mixed-client runs retain their normalized client proportions in separate cohorts to avoid blending different cluster compositions. When archived log samples include confirmed transaction counts, TPS is calculated as confirmed transactions divided by configured active workload duration, excluding network setup and post-workload collection wait; older reports without those counts retain their reported TPS. The runtime index compares every available client pair and shows confirmed transactions per node, confirmed cluster totals for standalone runs, and the configured target volume, calculated as target TPS/node × active seconds × node count (for example, 17 TPS × 180 seconds × 4 nodes = 12,240 target transactions). Startup readiness, source/binary size, and Hive pass rates remain categorical bar charts rather than being presented as continuous performance curves. WASIX is labeled separately from NEXUS native, Geth, and Reth. Charts use each module's report summaries, omit unavailable values rather than converting them to zero, and skip failed/interrupted runs. Runtime resource plots use container-scoped CPU/memory samples only; compliance is a pass/fail protocol result, not a performance score. Empty-block inclusion latency is the send-acknowledgment-to-first-receipt observation proxy described above.

Seaborn is optional and is used for the load curves and heatmaps when installed; the plotter includes a standalone SVG fallback, so no additional package is needed for normal use. To enable Seaborn styling, install it in the Python environment used to generate the charts with `python3 -m pip install seaborn`.

To keep a suite running after an SSH or terminal connection is lost, choose detached execution when starting it:

```bash
bash experiments/run.sh --detach
```

The runner still collects the experiment selection and configuration interactively, then starts the suite in its own session before shared setup begins. It prints a session ID and commands to follow or stop that session; the same commands can be run later with `bash experiments/run.sh --attach <session-id>` to reattach to its console log or `bash experiments/run.sh --stop <session-id>` to stop the suite and its child processes. Without `--detach`, execution remains attached to the current terminal as before.

## Interactive run configuration

After selecting experiments, the runner displays each selected module's proposed defaults in the same order. Press Enter (or answer `n`) to accept that module's defaults, or answer `y` to customize its settings; every custom field also accepts Enter to keep its displayed default. The prompts and validation finish before the shared setup runs, and evaluation mode (`7`) does not ask for run configuration.

| Module | Configurable run settings |
|---|---|
| Runtime | Native, WASIX, Geth, and Reth node counts (the client mix); one or more Contender workload scenarios; spammer accounts and target TPS per workload node; workload and collection-wait durations; chain ID; runtime iterations; whether generated network state may be cleared. Every workload/iteration pair is saved under a distinct run ID. |
| Empty block | Client selection, optional Diablo contract workload (`none`, `counter`, `dota`, `uber`, or `uber_v2`), chain ID, transaction-count groups, samples per group, maximum attempts, receipt/block timeouts, RPC poll interval, and network reset permission. The default standalone run uses native, WASIX, Geth, and Reth sequentially; customization can select one or more clients. Nonzero transaction groups use the local pre-funded Anvil test key by default; `EB_PRIVATE_KEY` or `--private-key` can override it. The key is passed only to empty-block runs, not shared setup. |
| Startup | Client configurations, iterations per configuration, chain ID, readiness timeout, system sampling interval, client images, optional NEXUS WASIX module, Wasmer executable, and permission to clear stopped shared-network data. |
| Compliance | Hive clients (default: Geth v1.15.11 and Reth v2.5.2), Hive image, parallelism, per-client timeout, and whether to build or reuse custom client/Hive images. |
| Size | Comma-separated `LABEL=DIR` source trees and `LABEL=FILE` binaries; paths containing commas are not supported by this prompt format. |

The standalone runtime scenario field accepts comma-separated Contender scenario paths such as `exp/uber,exp/uber_v2,exp/counter,exp/dota`; its defaults remain the two Uber scenarios, each with its own network lifecycle, metadata, and result directory. Selecting the full suite runs 50 client mixes across 4, 8, 16, 32, and 64 nodes: each client alone, WASIX/native, WASIX/Geth, WASIX/Reth, native/Geth, and native/Reth pairs, plus all four clients in equal shares. Each mix runs `counter` once at 17 TPS with 17 accounts per node for 180 seconds; `dota` once at 66 TPS with 66 accounts for 280 seconds; `uber` and `uber_v2` once each at 4 TPS with 4 accounts for 120 seconds; and `exp/value-transfer` once at 200 TPS with 10 accounts for 10 seconds (2,000 transfers per node). All runtime workloads use chain ID `12345` and a 900-second post-workload collection wait, for 250 runtime tasks total. The transfer-only Contender scenario sends 1 wei and is mounted from `experiments/runtime/value-transfer.toml`. Full-suite empty-block runs sweep 0, 1, 5, 10, 20, 50, 100, 200, 500, 1,000, 5,000, and 10,000 transactions for each client using a value-transfer workload plus each of the four contract workloads. Every client/workload/count combination is independently run three times (720 tasks total), each with its own run ID, log, and overview status row; each run uses one sample and at most two attempts, and each submission burst is capped at 300 seconds. Value-transfer transactions send 1 wei. Startup runs all five configurations (including host WASIX via Wasmer) five times, and compliance runs Geth v1.15.11 and Reth v2.5.2 once each with parallelism 5. The compliance selectors match the pinned image digests used by the other experiments: Geth `ethereum/client-go@sha256:798b7eb1bcef6d4be7576232beea63bf291450f48b025dc8fb5c6e37840e4364` and Reth `ghcr.io/paradigmxyz/reth@sha256:68e76b32ad9ac1a3de54984d6f15bbce2047a92a771ff4efbcd08ee8f9dbd4d1`. Empty-block accepts `uber_v2` as an optional contract workload alongside its existing options and runs each selected client separately with a distinct run ID; startup and empty-block iteration settings retain their module-specific meanings (repetitions per client configuration and samples per transaction-count group respectively).

Contract-call bursts use a fixed gas limit (`250000` by default) so Cast does not run `eth_estimateGas` separately for every future-nonce send. Set `--contract-gas-limit` on `experiments/empty-block/run.sh` to tune it for a workload; value-transfer runs keep their existing `21000` gas limit. Contract deployments use a `600000000` gas limit, and the shared network genesis block gas limit is `650000000` to allow storage-heavy workloads such as `uber_v2` to deploy.

For a nonzero target, one successful sample is a whole submitted burst whose transactions all have receipts; it remains successful if the burst is split across blocks. `block_samples.csv` retains one observation per block with each block's actual total transaction count and exact-match flag. `transaction_inclusion_samples.csv` records latency from Cast's send acknowledgment to the first receipt observation; `transaction_burst_samples.csv` records blocks spanned/distribution and burst completion latency from the first send acknowledgment to the last receipt observation. This is an observation proxy, not the exact consensus inclusion instant, because polling and RPC response time add delay. Receipt polling RPCs are bounded by the remaining timeout, and receipts observed before a timeout are written to the CSVs as partial evidence before the run fails. The report groups per-transaction latencies by target and whether the burst occupied one or multiple blocks. Empty-block TPS is emitted only between consecutively sampled block numbers; gaps are counted as skipped intervals rather than being presented as full-chain throughput.

## Modules

| Module | Entry point | Purpose and outputs |
|---|---|---|
| Runtime | `experiments/runtime/run.sh` | Starts a local mixed-client network, runs Contender workloads, records RPC/Prometheus samples, host/container metrics, structured logs, and reports availability by node/client. |
| Empty block | `experiments/empty-block/run.sh` | Runs a transaction-burst sweep, records actual per-block transaction counts, transaction inclusion latency and execution times, and writes block/transaction samples, raw events, derived samples, and coverage reports. |
| Startup | `experiments/startup/run.sh` | Repeats isolated client starts, measures time to the first successful `eth_chainId` response, samples system resources, and reports per-configuration statistics. |
| Compliance | `experiments/compliance/run.sh` | Builds the Hive runner and any selected custom WASIX client images, then runs `ethereum/engine` for pinned Geth/Reth releases by default. Workspaces, command lines, image identities, and per-client logs are retained. |
| Size | `experiments/size/run.sh` | Uses upstream `scc` to measure source-code lines and records compiled binary bytes. Missing source trees or binaries are reported as unavailable. |

Modules own their run lifecycle and experiment-specific collection/reporting scripts. Runtime and empty-block share the internal launcher and config/monitoring assets in `experiments/shared/network/`; neither module delegates to a legacy `scripts/v2` entry point.

### Runtime

The runtime module accepts `--linux-nodes`, `--wasix-nodes`, `--geth-nodes`, `--reth-nodes`, workload duration/TPS, and other local-run options; see `bash experiments/runtime/run.sh --help`. Standalone suite runs default to the `exp/uber` and `exp/uber_v2` Contender scenarios and two native plus two WASIX NEXUS nodes. The full-suite selection uses the client matrix and per-workload profiles described above. It builds from the local source tree and uses the metrics-server image prepared by the one-time setup.

Prometheus keeps host node-exporter data under `job="node-exporter-host",scope="host"`. Native and WASIX NEXUS containers run their own node-exporter endpoints, discovered as `job="node-exporter-containers"` with `node_index`, `node_service`, `client`, `runtime_variant`, and `scope="node_container_exporter"` labels. Every execution client’s own Prometheus endpoint is scraped as `job="execution-node-metrics",scope="execution_node"`; the target port is `9050 + node_index`, matching the generated client configuration. cAdvisor scrapes every execution-node container—including Geth and Reth—and adds `node_index`, `node_service`, `client`, `runtime_variant`, `container_name`, and `scope="container"` to container resource series. For example, query `container_memory_working_set_bytes{job="cadvisor",node_index="0"}`, `node_cpu_seconds_total{job="node-exporter-containers",node_index="0"}`, or a client metric with `job="execution-node-metrics",node_index="0"` in Prometheus at `http://localhost:9091`.

Runtime TPS and commit-to-submit ratio are derived from per-node structured logs using each workload's recorded spam-command start/end timestamps. Only unique transaction hashes received during that interval are treated as workload submissions; a submitted hash counts as committed only when it appears in the execution events for a block that is later imported. Consequently, setup transactions, unrelated block transactions, and post-workload activity do not inflate these two outcomes. The interval is the host-side Contender spam-command invocation, so it includes container/command launch overhead; the report records this basis and reports unavailable values when the client does not emit enough structured events. Reports summarize the per-node TPS and commit ratios.

### Empty block

The suite's empty-block defaults run native, WASIX, Geth, and Reth sequentially with transaction counts `0,1,5,10,20,50,100`; customize the module to select one or more clients instead. Each client run gets its own result directory and run ID. Running `experiments/empty-block/run.sh` directly still defaults to the `wasix` client. Set `--workload counter`, `--workload dota`, or `--workload uber` to deploy the corresponding Solidity workload using its entry in `diablo_workloads/bytecode.csv`, then run `Add()`, `update()`, or `checkDistance()` calls in place of value transfers; `--workload none` preserves the value-transfer experiment. Deployment is completed and checked for code before the count sweep, and its own inclusion latency is recorded separately from calls. `transaction_inclusion_samples.csv` records each deployment/call/transfer's client-side submission start, first receipt observation, block, gas used, status, and inclusion latency; `report.md` summarizes mean, median, p95, and reverted transaction counts. Latency ends when polling first observes a receipt, so it includes the configured polling delay (and, for bursts, time spent submitting the rest of the batch); it is an observed upper bound, not an exact consensus timestamp. Other sweep outputs and measurements continue to be collected for contract calls. Note: the current `uber.sol` `checkDistance()` implementation accesses `client_y[1]` after initializing only one `client_y` element, so those calls revert; the experiment still records their inclusion latency and failed receipt status. Nonzero counts use the pre-funded default Anvil account unless overridden with `EB_PRIVATE_KEY` or `--private-key`. This is a publicly known development key; never use it on a live network or with real funds. `--reset-network` explicitly permits removal of pre-existing generated `data_v2/` and `startup_v2/` state. On successful archival, the module removes only its generated network state so the next selected module or client can start cleanly; failed runs retain state for diagnosis.

### Startup

The default startup configurations are Geth, Reth, NEXUS native, NEXUS in Docker/WASIX, and host NEXUS WASIX via Wasmer. Reth uses the pinned GHCR digest `ghcr.io/paradigmxyz/reth@sha256:68e76b32ad9ac1a3de54984d6f15bbce2047a92a771ff4efbcd08ee8f9dbd4d1`; override it explicitly when comparing a different version. NEXUS Docker configurations use local `wasix-eth-linux:latest` and `wasix-eth-wasix:latest` images; setup reuses those images when present and otherwise builds them from the local `target/` binaries. The host Wasmer configuration uses `wasix_eth/target/wasm32-wasmer-wasi/release/wasix_eth.wasi.wasm` by default (or `NEXUS_WASIX_WASM` when set); standalone startup runs include it when the module and Wasmer are available. `--timeout`, `--iterations`, `--configs`, image paths, and other options are listed by `bash experiments/startup/run.sh --help`.

The measured endpoint is the first `eth_chainId` response that matches the configured chain ID. Image/data preparation and genesis initialization are performed before timing for all clients; the timed interval starts immediately before launching the client process/container. Image references and IDs are recorded for reproducibility.

For diagnosing an RPC readiness failure, run a single configuration with `--keep-failed-containers`, for example `bash experiments/startup/run.sh --configs reth --iterations 1 --keep-failed-containers`. A failed Docker client is left running (or retained if it exited) after its logs are collected; the runner prints the host RPC URL and a `curl` probe. The port and container name are also recorded in `iterations/reth/1/state.json` and `result.json`. Remove a retained container when done with `docker rm -f <container-name>`. This option is intended for focused debugging, because a retained running client can affect later measurements.

### Compliance

The compliance module builds `hive-custom:latest` from `hive/hive.dockerfile` and builds `z4l3s5i0/wasix-eth-linux:latest` and/or `z4l3s5i0/wasix-eth-wasix:latest` only when those custom Hive clients are selected. Its defaults use Hive's version selectors `go-ethereum_v1.15.11` and `reth_v2.5.2`, matching the Geth and Reth image revisions pinned by startup and the shared network. The Hive command uses `--sim ethereum/engine`, the selected client, `--sim.parallelism`, and `--docker.pull=false`, following the Hive command-line guide. Per-client results and logs are kept separately; any client failure makes the compliance stage fail.

### Size comparison

The source measurement uses Boyter's upstream `scc` v4.1.0 and sums its machine-readable `Code` counts; `.git`, dependency/vendor, build-output, generated, and test paths are excluded. The default source tree covers `wasix_eth/`; default binary candidates are `wasix_eth/target/release/wasix_eth` and `wasix_eth/target/wasm32-wasmer-wasi/release/wasix_eth.wasi.wasm`. Setup builds these NEXUS binaries once when needed for a selected module. Provide additional or different paths with repeated `--source LABEL=DIR` and `--binary LABEL=FILE` options, or use `GETH_SOURCE_DIR`, `RETH_SOURCE_DIR`, `WASIX_ETH_NATIVE_BINARY`, `WASIX_ETH_WASIX_BINARY`, `GETH_BINARY`, and `RETH_BINARY` environment variables. The report lists missing inputs as unavailable, never as size zero. Docker image size is intentionally omitted because image layers include runtime dependencies and are not comparable to compiled client size.

## Dependency and setup notes

`experiments/setup.sh` supports Ubuntu/Debian Linux. It installs or verifies the shared command-line tools (`curl`, `wget`, `git`, `jq`, `openssl`, Python 3, and `lld`). When the size module is selected, setup installs or verifies upstream `scc` v4.1.0 from its official Linux release, validating the pinned SHA-256 checksum without requiring Go. When a selected module needs client binaries, setup installs Rust stable via `rustup`, `cargo-wasix`, and `wasixcc` v0.4.7; `wasixccenv` installs the compiler executables into the user Cargo bin directory and downloads the LLVM toolchain and WASIX sysroot before any `cargo +stable wasix build --release` invocation. Setup also installs or verifies Wasmer 7.4.2 under the current user's Wasmer directory; these binary directories are added to the suite process `PATH`. Docker and Compose v2 are installed/verified only when a selected stage needs them; the Docker daemon must be usable by the current user. For runtime, empty-block, and startup selections, setup pulls shared external images including cAdvisor and builds `wasix-eth-metrics:latest` once. Startup-specific NEXUS images use cached local images when available and are otherwise built from `wasix_eth/Dockerfile.linux` and `wasix_eth/Dockerfile.wasix` using the local `target/` artifacts; setup does not pull `wasix-eth-wasix` from Docker Hub. When native/WASIX target binaries are absent, setup builds them once. Hive client and Hive runner images are prepared by the compliance module.

The setup script requires network access to install the pinned `scc` release, Rust stable, `cargo-wasix`, `wasixcc` v0.4.7 and its LLVM/sysroot components, and Wasmer 7.4.2, and to pull Docker images/build the Hive runner when selected. Host Wasmer startup measurements additionally require a compatible WASIX module; external binary comparisons require the respective files. Docker-backed stages require a running daemon accessible to the current user.

## Metric coverage

| Source | Metrics | Experiments |
|---|---|---|
| Node-level Prometheus | Sync status, head block, peers, blocks imported, transactions committed, mempool size, rejected transactions, gossip messages, P2P bytes, RPC requests | Runtime, empty block |
| RPC-derived | Node status/RPC availability, latest block, chain ID, peer count, gas price, syncing status | Runtime, empty block |
| System-level | CPU utilization, memory usage, disk I/O, network throughput, load averages, context switches | Runtime, empty block, startup |
| Log-based | Transaction hash, sender, gas used, elapsed time, block number, transaction count, peer ID, download type, TPS, commit-to-submit ratio | Runtime, empty block |

System values are labeled `host`, `container`, or `process` according to attribution. Host node-exporter metrics are never labeled as container measurements; cAdvisor provides per-container CPU, memory, disk, and network metrics with node/client labels, while the NEXUS containers' own node-exporter endpoints provide node-scoped OS metrics. Load averages and context switches stay host-scoped rather than being copied to each client. Missing values are omitted and shown as unavailable/partial in reports, never substituted with zero. A real observed zero (for example, an empty block’s transaction count) remains a valid measurement.

Prometheus exposition names are retained raw and are not normalized unless client semantics are verified. The current Geth inventory and equivalence mappings are explicitly unverified in `scripts/v2/GETH_METRICS.md`; raw-series presence does not claim metric equivalence. Structured `[EXP]` log fields are currently available from the custom NEXUS clients; clients without those events show the corresponding log fields as unavailable. Empty-block TPS is derived only across consecutively sampled block numbers; its commit-to-submit ratio uses receipt-confirmed test hashes.

## Implementation status and remaining gaps

### Implemented

- Interactive ordered dispatch, one-time selection-aware setup, shared run IDs, and isolated output folders.
- Evaluation-only dispatch through `experiments/run.sh` to regenerate selected modules' reports from saved runs without setup or workload execution.
- Runtime lifecycle, RPC status samples, raw Prometheus retention, secure metric ingestion for derived/system/log samples, host/container system collection, structured log parsing, and per-node availability reports.
- Separate host, per-node NEXUS node-exporter, and cAdvisor scrape targets, with execution-container labels preserved in Prometheus time series.
- Per-client execution metrics endpoints scraped with indexed ports and `node_index`, `client`, `runtime_variant`, and `scope` labels.
- Empty-block transaction submission, receipt polling, actual block counts, millisecond execution-time log parsing, and labeled block/log/system outputs.
- Repeated startup benchmarks, readiness timing, per-process/container and host-scoped metrics, image identity, and summary statistics.
- One-shot Hive `ethereum/engine` execution for pinned Geth/Reth releases or selected custom clients, with per-client logs and exit statuses.
- Separate `scc` source-code-line and compiled-binary size measurement scripts with unavailable-input reporting.

### Remaining limitations

- Docker-backed network, Hive, and startup end-to-end runs have not been performed as part of this code change; validate them on a Linux host with Docker available.
- cAdvisor requires privileged access to the Linux Docker host and its cgroups; validate container series on the target Docker environment, especially when using Docker Desktop/WSL.
- Prometheus metric equivalence across all clients is not verified. Geth mappings and semantics remain raw/unverified, and some client-specific counters are unavailable.
- Structured log coverage varies by client; peer/download events, transaction senders, and gas/timing fields are not guaranteed for non-NEXUS clients.
- Per-client network throughput is available from Docker stats for containers; for host Wasmer, host throughput is measured but process-level network attribution is unavailable.
- External Geth/Reth source trees and compiled binaries are not vendored. Supply paths to compare them; the report will preserve missing values explicitly.
- Host-scoped load averages/context switches and telemetry collection overhead are not equivalent to client-attributed measurements.
